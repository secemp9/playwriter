# Browsing like a human: design

Why playwriter has `observe()` / `act.*` / `find()` / `explain()`, a human policy, and an automatic action report — and what each piece is built on.

## The problem

Models without vision, and weaker models generally, drove real products through playwriter and failed in a small number of ways. These are taken from ~530 recorded sessions, not hypothesised:

| Failure | What it looked like | What was missing |
|---|---|---|
| Jumping with `page.goto` | 15 reload+click cycles to "reproduce" an SWR stale-cache bug that only a pure SPA flow triggers; the reload wiped the cache every time | a navigation rule, and a report that says "full reload" |
| Acting before the app settled | posting while the reply still showed "Processing: Fetching reviews" → interrupted reply, duplicate post, forked thread | a busy signal and a wait-until-idle primitive |
| Batching | goto + fill + click + post in one call, then a timeout with no idea which step failed | one action per call, with a report after it |
| Misreading the page | "everything works" while product images were broken; DOM numbers instead of what a person sees | states, visibility, image load state in the observation |
| Faking the repro | `pointer-events: none`, network interception, synthetic events, curl to the API | a policy that refuses forced state and API bypass |
| Claiming success | ✅ next to steps that timed out | a report that says NOT SETTLED / FAILED / NO VISIBLE CHANGE |

The research on text-only web agents points the same way (WebArena, AgentOccam, WorkArena/BrowserGym, Browser Use, Playwright MCP, Chrome DevTools MCP): changing only the observation and the action space roughly triples weak-model success (AgentOccam: Gemini-1.5-Flash 11.6% → 33.7%); pruning the action set (no `goto`) is the largest single gain; weak models get worse as instructions grow; every shipped tool waits for a quiet page after each action and reports what changed; refs must be stable.

## Hard constraint: never modify the page under test

Everything here reads through CDP (Accessibility, DOMSnapshot, DOM, Network, Page, Runtime events) and through a CDP **isolated world** (`isolated-world.ts`): it shares the page's DOM — so a MutationObserver installed there sees every mutation — but has its own JS globals that page scripts cannot see. No elements, no attributes, no main-world globals or listeners, no init scripts, no fetches from the page. Input is real input only: a native `<select>` is opened with a click and chosen with the arrow keys and Enter, a hidden control is operated through the `<label>` HTML forwards clicks from, a file is attached through the file dialog its control opens. Pixels are read from one viewport capture, never a clipped one (Chrome takes a clipped capture by moving its emulated viewport). Pins and picks use Chrome's own element picker (`Overlay.setInspectMode`); recordings draw the pointer at encode time from the inputs that were dispatched. Tests assert the page's own globals, element count and its own MutationObserver records are unchanged after observing, settling, explaining, labelling, recording and acting.

**No user gesture either.** Playwright runs every script it puts in the page — `page.evaluate`, every locator read and the actionability checks of every locator action, `page.title()`, a new element handle's preview, `page.screenshot()`'s preparation — through `CRExecutionContext.evaluateWithArguments`, which sends `userGesture: true`. Measured on a fresh page, each of them turns `navigator.userActivation.hasBeenActive` true: the page then counts as clicked, and may prompt "Leave site?", play sound, or open popups and file dialogs that a person who only looked could never trigger. Human mode therefore runs no Playwright script in the page at all. `readPage(fn)` is the read path: a `Runtime.evaluate` of the function on the element (or the document) in the page's own world, without a gesture and under V8's side-effect check, so nothing the function calls can have an effect, and with V8's own time limit, so nothing it calls can hold the tab. It runs in the page's world, not an isolated one, because measured, the first touch of another frame's window from an isolated world under the check wedges the renderer, while the page's world has a context in every frame already; under the check the page cannot observe the read.

**Not even when the page logs an element.** Playwright's server previews every element handle it creates by building its injected script in the element's world and calling it as a user gesture — and the page creates such handles itself: each `console.log(element)` (`crPage.ts` `_onConsoleAPI`) and each file chooser. Measured on a page that logs an element: the page became user-activated, and Playwright's injected script added 13 capture listeners (pointer, mouse, touch, `click`, `contextmenu`, and its own `__playwright_global_listeners_check__`) and a MutationObserver to the page's own world. `playwright-server.ts` replaces that preview before playwriter connects: the same text, from a self-contained read in the handle's own context, under the side-effect check and without a gesture.

## Architecture

```
execute(code)
  ├─ code-policy.ts     Babel scope analysis of the code: actions (aliases and helpers followed), navigations,
  │                     forced state, API bypass, unanalysable page code. Human policy refuses before anything
  │                     runs. Also replaces /\breturn\b/.
  ├─ page-probe.ts      per page: PageFrames (a session and an isolated world per frame, OOPIFs included),
  │                     PageWatch, DialogController, PinTracker, act history; one session-wide RefRegistry
  ├─ (while it runs)    a raw-input tap on Playwright's client instrumentation counts actions at run time and
  │                     follows the tab the input went to; act takes its before-picture at dispatch; in human
  │                     mode a guard on Connection.sendMessageToServer refuses every protocol call that would run
  │                     Playwright's script in the page or change it (playwright-call-effects.ts)
  ├─ sandbox code       observe / find / explain / act / pickElement / docs / net.requests …
  └─ (after input)      PageWatch.settle (from the end of the last input) → observe → diff → renderActionReport
```

## What came from oh-my-pi's browser tool, and what did not

The omp tool (MIT) was studied module by module. Its strengths are fail-fast, attributable errors and a few primitives; the fork's PageModel was already the stronger perception substrate (omp's `observe()` has no geometry, occlusion or stable ids).

| omp capability | Taken | How |
|---|---|---|
| AX states in observe (`focused`, `checked`, …) | yes | `ax-states.ts`, everywhere a node is rendered |
| explicit stale-element errors | yes, stronger | stable refs per node, error names what happened and suggests the new ref |
| click actionability: stable box, `elementFromPoint` occlusion, "covered by <x>" | yes | `DOM.getNodeForLocation` at several points; the cover is named by role/name or layer |
| dialog policy with pending confirm/prompt | yes | `dialog-controller.ts` |
| request log + response bodies | yes | `net.requests()` / `net.request(id)` |
| readable extract `outline` / `filter` | yes | `getPageMarkdown({ outline, filter })` |
| `pushState` helper | no | `act.spaNavigate` clicks the page's own link to the route, or refuses: calling a router or `history.pushState` is not something a person can do |
| timeout diagnosis naming the stalled op | partly | inner Playwright timeouts fire first with Playwright's reason; the abort signal stops act; the report says what is still pending |
| aria snapshot text diff with revisions | no | replaced by the semantic element diff in the action report; text diffs are opt-in only |
| screenshot `annotate` / `ifChanged` | partly | `screenshot({ ifChanged })` and `diffScreenshot()` return the changed share and box, readable without vision; labels are `screenshotWithAccessibilityLabels` |
| worker-per-tab isolation, freeze on turn end | no | a different runtime architecture; not a perception problem |
| stealth patches | partly | patchright for the user's own Chrome; a `browser new` presents the binary's own headed identity (`new-browser.ts`, `chrome-identity.ts`) |
| axe a11y audit, web vitals | yes | `audit()` (axe-core in the isolated world, `page-audit.ts`), `perf.vitals()` (`perf.ts`); emulation stays Playwright's, at `browser new` launch |

## The policy

`human` (default for MCP and CLI sessions; the executor class defaults to it too), `fast` and `debug`. For MCP sessions the model chooses `human` or `fast` per session with the `browser` tool (`use`/`new` with `mode`); the default is `PLAYWRITER_POLICY` (`human`, `fast` or `debug`), else human. CLI sessions take `--policy human|fast|debug`; `debug` only the user turns on. A session keeps its mode until the next `use`/`new`. Human mode refuses, before running anything: more than one action (helpers called twice or in a loop count as several; aliases are followed by binding; `webmcp.invoke` is an action, `act.switchTab` and `act.dialog.policy` are settings), `page.goto`/`reload`/`goBack`/`setContent` and in-page `location`/`history` jumps on a non-blank page (unless `act.open(url, { reason })` / `act.reload({ reason })` / `act.back()`), forced state (`page.route`, `fulfill`, `net.delay`, init scripts, DOM/style/storage writes and synthetic events inside page-evaluated code, `setCookies` / `clearCookies` / `setStorage` / `clearStorage` / `loadState`, `screenshot({ fullPage })`, React internals, `ghostCursor.show`), API bypass (`fetch`, `page.request`, `http` modules) and page code it cannot read (page functions passed as variables, wrappers, `eval`, run-time strings). While the code runs, a second action is refused before it is sent — raw Playwright input included — and `getCDPSession()` only reads (reads include `Performance.*`, `Profiler.*`, `Tracing.*` and `IO.read`; `Page.captureScreenshot` only without `clip` / `captureBeyondViewport`). Reading without Playwright's script is never restricted. Act refuses input while the page itself says it is busy or a native dialog waits for the agent, refuses a ref whose element no longer reads as it did when the model saw it, repeats an action that sent data-changing requests only with `{ again: true }`, and refuses a fourth identical attempt after three produced no visible change.

Human mode also runs no Playwright script in the page, before the code runs (by API name) and while it runs (by protocol call, at `Connection.sendMessageToServer`, for every call made in the run's async context — the code's own, a helper's, act's, and the ones the code leaves running after it returns). Playwright reads, element actions, screenshots, `waitForSelector`, printing, emulation, permissions, exposed functions, fake clocks and raw CDP sessions are refused there (`screenshot()` and `pdf()` capture and print through CDP instead); `page.mouse` / `page.keyboard` input is not. Pages of another browser context (`browser.newContext()`) are not under test and not guarded.

`fast` is for testing on localhost. Its code policy is debug's: nothing is refused (multi-action scripts, `page.route`, init scripts, storage and DOM writes, raw Playwright, `page.goto`). act.* drops human pacing and keeps every correctness check: one straight pointer move (Playwright's `page.mouse.move`, one awaited `Input.dispatchMouseEvent`) then the press with no hold delay; keys sent one after the other's ack; no random pauses; the wheel's whole remaining distance in one event; a drag as 5 evenly spaced held moves (Chrome's `Input.dragIntercepted` arrives before the second move's ack, so the drag data is in without waiting); select and colour-chooser keys without delays. The hit test, cover and disabled refusals, the busy guard, native and file dialogs, stale-ref checks and the report stay. Touch input on a phone preset keeps its stroke timing (a swipe's speed is what the page reads as a fling; not measured); only the pauses between swipes go. Several actions in one call: when an input action starts, the records since the last report get a report of their own (a fast settle, their events, a look, the change list against the first one's before-picture); the call's report covers the last action and anything that could not be told apart (raw Playwright input, a tab or download opened, a dialog, a closed page). Recording is allowed: the video shows the fast input.

Settle in fast mode is page-watch's `pace: 'fast'` (CHANGELOG 122): no quiet windows; the page's queued work (MessageChannel round trips in each frame's isolated world), its MutationObserver journal and each caused request's own CDP events decide, and the only timer is the cap. Human mode is unchanged: settle waits for quiet windows (300 ms DOM, 500 ms network, from the end of the input) and keeps the 2 s held-iframe-document and 3 s stalled-asset rules.

Waits in act.* that are not a person's pacing wait on state, in both modes, each with a cap labelled as one: a native dialog (the dialog controller's change event), a wheel or swipe's scroll (`scroll`/`scrollend` watched in the isolated world: ended, or no scroll by the second animation frame; cap 900 ms), a checkbox toggling (its checked state re-read on each mutation/input/change; cap 1200 ms), a select's value after a choice (re-read on each change; human mode keeps its 500 ms glance as the window, fast mode stops at the first read that shows the choice), `act.back()` (the main frame's navigation committing; cap 1–10 s). The colour chooser's `:open` and a select's open list are read once right after the input's ack: measured on Chrome 145, both are set by then (5 of 5), and the colour input holds the typed colour as soon as the last key is acknowledged.

## Known limits

- A colour input with a `list` (suggested colours) cannot be set. Chrome opens its swatch popup for it (`color_suggestion_picker.js`), whose keydown handler cancels every key but the arrows and Escape, so no key picks a swatch or "Other…"; page mouse input goes to the page widget, which closes the popup on mousedown (measured on Chrome 133, headless and headed). A colour input without a `list` is set through Chrome's colour chooser page popup, whose keys Chrome forwards from the page.
- `readPage` with a ref inside a **closed** shadow root needs Chrome's console helpers to hand the element over (`$_` is the only way a `Runtime.evaluate` expression — the only call V8 bounds in time — receives an object). Chrome gives them only to fully trusted debugger clients, so over the extension such a read is refused (getCleanHTML, snapshot and explain still read the element); on a direct connection the read runs with the helpers (`$`, `$$`, `keys`, …) defined on the window until it returns, where the read can see them and the page cannot keep them. A page that defines its own `$_` hides that element.
- Locating a `readPage` refusal re-runs the function up to about twice the base-2 logarithm of the calls it makes before it is stopped, within 3 s; past that the error says it was not located. The search assumes the function runs the same way each time (the page's own code runs between the re-runs); a run that ends neither at its stop nor at the check makes it report the refusal as not located.
- A service worker's or shared worker's own requests are not journaled, through the extension too. Chrome attaches those workers to the browser, not to the page (Playwright's page sessions detach any other target type, and chrome.debugger attaches only tabs), and they serve every tab of their origin, so none of their requests belongs to one page's action. A page request that a service worker answers is journaled on the page's session like any other. Dedicated workers, and the workers they start, are followed.
- Chrome does not report some worker errors at all: when a page terminates its worker inside the worker's own `error` handler, that error leaves no trace — no `Runtime.exceptionThrown` reaches the worker's session and no `Log.entryAdded` the page's, though the worker's session was live (measured over raw CDP on Chrome 149, the Chrome a `browser new` launch runs, and through the extension; workers-relay.test.ts asserts it). The lab's errors.html (ERR-T4) is that case, in `browser new` and through the extension alike: the page's own text is the only trace. A worker the page terminates while its script is still downloading: Chrome keeps fetching and never reports the end of that request or of the worker target, so the request stays open in the journal (measured with a 3 s script terminated after 300 ms). A dedicated worker's script entry stays open in `net.requests()` until its session closes; a service worker's stays open but never holds settle.
- An iframe's document that Chrome has not delivered is reported, not waited for. Measured on MDN: its live examples' documents (`*.mdnplay.dev/…/runner.html`) answer with `Clear-Site-Data: "cookies", "storage"` (read with curl as an iframe navigation), and Chrome delivers such a document only after it has cleared that site's data. In a user's Chrome 149 it delivered the 15 examples one by one over more than a minute after the page had loaded; in a fresh Chromium or Chrome profile it never did (headless and headed, without playwriter too: no response and no response headers for 70 s). The journal keeps those requests open until Chrome answers (`net.requests()` shows no status), settling ends without them once they have had no answer for 2 s, and the reports name the iframes by ref. A page whose load event waits for such an iframe (an iframe in the HTML, not one added after load) stays loading: Chrome marks its document busy, and act.* waits as for any busy page. How long Chrome holds such a document depends on the browser, not only on the page: a local page answering with the same header was held 45 s and more by a Chromium 145 (headless) launched 1 s or 4 s earlier, and delivered in about 0.1 s once the browser had run 7 s or more (measured). The tests therefore never answer the runner documents (network-lab-fixture.ts), which leaves Chrome in the same state: the request sent, no response.
- A download in a cloud browser, or in a browser on another machine, stays on that machine: no CDP command reads a downloaded file, and the body of the request that became a download is not kept (measured: `Network.getResponseBody` on it fails with "No resource with given identifier found"; Chrome ends the request `net::ERR_ABORTED` and hands the body to its download manager). The report line and `downloads.save` say where the file is.
- On the default engine the page can tell it is being driven: Playwright's server enables CDP's `Runtime` domain on every page session, and Chrome then builds previews of console arguments, which runs the page's own getters (measured: a page logging an `Error` with a `stack` getter every 100 ms saw the getter run 22 times). This is the known way anti-bot scripts detect CDP. Playwriter does not enable it itself (the session rules forbid `*.disable`, and Playwright's server needs it); the patchright engine (`PLAYWRITER_PATCHRIGHT=1`) never enables it, and human mode runs on it.
- On the patchright engine, console messages and uncaught exceptions are not journaled and `getLatestLogs` is empty: Chrome sends `Runtime.consoleAPICalled` / `exceptionThrown` only to sessions that enabled `Runtime`, `Log.entryAdded` carries no console calls (measured: 0 entries while the page logged 10 times), and enabling `Runtime` is exactly the detectable step patchright avoids (measured: the `stack` getter ran 0 times without it, 26 times in the second after it).
- The `HIDDEN` line can only show what Chrome reports. Through the extension it comes from `chrome.tabs` / `chrome.windows` (the page cannot be asked: Playwright's focus emulation makes `document.visibilityState` read `visible` in a background tab, measured on Chrome 149); a browser playwriter launched does not throttle background tabs (~60 requestAnimationFrame callbacks per second, unclamped timers, measured) and says nothing; over direct CDP which tab is in front cannot be read, and a timeout there says so. `page.bringToFront()` in headless Chromium focused a minimised window but left it minimised. A window that is not on screen is not reported either (measured on Chrome 149 and Chrome for Testing 145, headed under Xvfb, through the extension): on an i3 workspace that is not shown, `chrome.windows` gives `normal`, the same bounds and `focused: false`, as for a shown window another program has the focus of; `chrome.windows.update({ state: 'minimized' })` changes nothing without a window manager that iconifies; and under X11 the page's own `visibilityState` stays `visible` while its window is unmapped. The colour chooser never opened in a background tab (HIDDEN names that case), nor, twice, in a window mapped again without X input focus, which Chrome still reports as normal, focused and active — there `page.bringToFront()` brought it back. A window on an i3 workspace that was not shown still opened it.
- While another extension's frame is in the page (a password manager's autofill menu), no extension debugger can do anything on that tab — not read, not press Escape, not attach (measured: "Cannot access a chrome-extension:// URL of different extension"). Only the user or that extension can close it; nothing tells an extension the frame left, so it finds out by attempting the attach (a browser-side check that reaches no page), and after 5 minutes only on tab events and the model's calls. The input that triggered the cut is half-delivered (measured: `pointerdown`, `mousedown`, `focusin`, never `pointerup` / `mouseup` / `click`; keys after the cut lost). `PLAYWRITER_DIRECT` is not subject to it. The extension's first attach (icon click, reconnect after a relay restart) still removes other extensions' iframes from open shadow roots to make the attach succeed (`removeRestrictedIframes`, upstream issue #18) — a write to the page; the re-attach after a cut never does. Over direct CDP such a menu frame makes the action report wait the full settle cap (`NOT SETTLED after 5041ms — waiting on GET /menu.html`). The check that the cutting frame is no longer loading runs for 10 s after the cut; a frame still loading after that is taken as abandoned.
- The extension reloads itself into a newer build of its folder only while it is connected to the relay and controls no tab; an extension built before self-reload (no build in `browser list`) needs one ↻ on its card in chrome://extensions, and a copy not loaded from the fork's folder (a Chrome Web Store install) never has a build id or reloads itself. Developer mode must stay on: Chrome disables an unpacked extension the moment it is turned off, and one loaded with `--load-extension` or `Extensions.loadUnpacked` while it is off is disabled by its first reload and stays disabled after a restart (measured on Chrome for Testing 145 and Chrome 149); `playwriter browser start` turns it on in its own profile. A Playwright client of the relay that controls no tab is not waited for: the reload drops the extension's connection, and such a client reconnects on its next call, as after a relay restart.
- A crashed tab is replaced, not revived: the recovered page is a new tab in the same context (cookies and storage kept), without the crashed tab's history. The PAGE CRASHED line names the URL and when; Chrome's termination status (`Target.targetCrashed` `status` / `errorCode`) is not read: Chrome sends it only to a browser-level session with target discovery on.
- If the controlled tab closes during a call, observe, find, act, webmcp, pickElement and waitForPageLoad follow the replacement tab, but a raw Playwright call on the old `page` object right after the close still fails with Playwright's own "closed" error.
- When the tab closes during the press of an input (Chrome took the tab before confirming the mouse button or key-down), whether the page got the press cannot be told: the action fails saying so, and the model reads the page that is controlled now. A debugger cut is not such a close: the tab stays open, and the action says how far the input got (DEBUGGER CUT).
- Full-page screenshots are debug-only (they fire resize events in the page, measured). An element outside the window is not captured in human mode (`act.scrollTo(ref)` first); of a partly visible element only the visible part is (said in `note`). `screenshot({ ref })` on a pinch-zoomed page is refused. `ifChanged` baselines live in the MCP process per tab and scope.
- `pdf()` is visible to the page: beforeprint, the print media query turning true and back, afterprint fire (measured on Chrome 149; no resize, no ResizeObserver, no user activation) — the same as a person printing. `perf.metrics()` counts from the first `Performance.enable`, so its first call reads about 0 for counts and durations. Web Vitals cover the top document only; INP sees interactions from 16 ms, and from before playwriter observed the page only those Chrome buffered (≥ 104 ms). CDP's `PerformanceTimeline` is not used: through the extension `PerformanceTimeline.enable` answers -32601, and it has no event timing or long animation frames.
- React render counts are not available: nothing in the fibers counts commits (measured on React 19.2.7 dev: after 3 clicks a counter's `actualStartTime` changed once, and components that bailed out show the same value); counting needs React DevTools' hook installed before React loads, an init script, which is a page modification.
- `audit()` keeps the renderer's main thread busy while axe runs; a page watching `longtask` entries sees it (up to ~1 s per task on a 15 000-element page). It does not run `css-orientation-lock` (axe's CSSOM preload would download cross-origin stylesheets again). `clickable-without-keyboard` sees click listeners on the element itself, as observe does, so a React app's delegated `onClick` on a `<div>` is missed. An iframe hidden from screen readers is not audited (listed under NOT AUDITED). axe-core's rule internals are read, so it is pinned to 4.14.0 and a test fails on another version.
- `cookies()` without `urls` lists what the current URLs send; a cookie of another path appears only with `urls` (saveState includes every path of the page's hosts). `saveState` saves one localStorage per origin: cross-site iframes' partitioned storage and sessionStorage are left out (listed in `leftOut`); `loadState` loads localStorage only into origins open in the tab, and merges. `clipboard.read()` returns text only, and through the extension needs an extension with the `clipboardRead` permission (the update's new permission warning disables a Web Store extension until the user accepts it). Over a headful direct CDP browser the private clipboard reader opens a window for the read.
- WebMCP needs Chrome ≥ 149 with WebMCPTesting and DevToolsWebMCPSupport (measured on 149.0.7827.114; the bundled Chromium 145 has neither). `webmcp.events()` starts at the first `webmcp.*` call on a tab (the domain is enabled lazily). Chrome 149's `WebMCP.enable` replays only the local root frame's tools and sends no `toolsRemoved` on navigation; the first gap is filled with `getTools()` in the isolated world (a WebMCPTesting API), the second by dropping a frame's tools on `Page.frameNavigated` / `frameDetached`. Annotations come only from the CDP announcement. A `webmcp.invoke` (or `act.*`) function kept in `state` still belongs to the call that created it.
- `allowedDomains` does not cover WebSocket or WebRTC connections (CDP Fetch does not hold them). A `userAgent` claiming another OS keeps this computer's `navigator.platform` in workers, and one claiming another Chrome major keeps the real version in client hints (the reply says so). `device` accepts only Chrome presets. WebGL shows the real GPU only on Linux with a usable EGL driver; otherwise SwiftShader. The startup launch with `PLAYWRITER_BROWSER=new` overlaps only the model's think time: a client calling `execute` right after `initialize` got its first `observe()` of about:blank 2.19–2.31 s after spawn (measured under load), against 2.28–2.36 s when the client called `browser new` itself.
- With a touch `device` (a phone or tablet preset), act taps, swipes and drags with a finger and refuses `act.hover` and right and middle clicks: Android Chrome opens a context menu on a long press, but Chrome's touch emulation never does (a press held 0.9–1.7 s gave a plain click, measured on Chrome 149), so no act call can give a touch page its context menu.
- act.select on macOS Chrome is not measured: if the list does not open on the click it refuses rather than choosing with keys. With two options sharing a label the open list's highlight is checked by label only; labels whose start cannot be typed on a US keyboard (e.g. "東京") are reached with arrow keys only. An editor that moves the caret on click is refused before typing. A scroll area's distance is capped at what it can scroll when the wheel starts; content the page adds meanwhile is reported, not chased.
- A mouse event's `clientX` / `clientY` are whole CSS px in Chrome, so a page reading them sees a point within 1 px of a fractional point act asked for.
- Observe: listener-only targets are listed only when they contain no other control, and focusable regions (scroll areas, dialogs, landmarks, live regions) are not targets. A clickable card that also contains a button is a container (the button has the ref), except a surface that also listens for the press itself (pointerdown/mousedown/touchstart) around exactly one control, such as a custom slider's track. Delegated items are recognised when the container's listener serves at least 3 visible children of the same tag and first class. An image inside a named control is not listed even when its alt differs from the control's name. An unseen image (a side ≤ 1 px of its rendered box, after transforms, or no box) is not listed, but its alt can still name its table cell or link: Chromium names a cell after its content, so a cell holding only a 1×1 `alt="tracking"` pixel reads `cell "tracking"`. A standalone `snapshot()` measures images with one `DOM.getBoxModel` each (it has no layout read to reuse); observe and act pictures use the layout they already read. A row's context is cut at 50 characters (find() searches the whole row). An `aria-describedby` popup without `role=tooltip` is plain text while it shows. One-time-code and card fields stay masked even when the page shows them in clear.
- Busy and settle: an element is a skeleton only with evidence (an aria-busy ancestor, or ≥ 2 siblings with the same animation); a lone shimmering block is still a spinner. The in-settle loading log uses the frame's own `elementFromPoint`, so what covers a whole iframe from outside is not checked there (the final BUSY line uses the full hit test). A determinate bar that advanced after the action and then stalled stays "advanced since the action" until the next action.
- Query handlers read the DOM tree CDP sends, which omits whitespace-only text nodes: `text/` compares with spaces removed. `snapshot({ diff })` compares diff snapshots only (a plain snapshot does not advance the revision), and not with `frame` or `search`.
- What a call costs: each action takes two pictures of the page (before and after) and waits for it to settle. On a large page each picture costs about 0.5–1 s (Wikipedia about 0.9 s), and settle waits at least 0.5 s of quiet after the input; pointer motion and typing run at human pace (about 75 ms per key). Budget about 2–3.5 s per action on a large site plus typing; observe() and find() take one picture each. `DOMDebugger.getEventListeners` per frame (18–80 ms), the transparent-control capture (~160 ms on Wikipedia) and settle's shadow-root discovery (85–170 ms) were measured and kept: each cache or clip that would remove them would change a verdict. `browser new` waits for Chrome's GPU process before its first page: 4–10 ms on an idle computer, 1.4–2.1 s when many Chromes start at once (32 in a burst, measured); without the wait, pages there did not paint. Fast mode keeps the two pictures and drops the pacing and the quiet windows: a click took 389–443 ms, a fill 399–476 ms and a select 496–588 ms on the lab pages (Chromium 145), against 1369–1409, 2573–2743 and 2401–2533 ms at human pace.
